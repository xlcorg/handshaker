# Stream call живёт в ядре; IPC — адаптер; один канал на вызов

## Контекст

Стриминговые методы (server / client / bidi) добавляют к Send долгоживущий объект:
вызов открыт, пока сервер не завершит его или пользователь не отменит; у него есть
управление (Send message, Half-close, Cancel) и Stream store — все inbound и outbound
messages в сыром виде, без лимита (решение тикета 08). Где-то этот объект должен жить,
а фронт должен получать сообщения по мере прихода.

Три вопроса решались вместе:

1. **Кто владеет открытым вызовом** — ядро или Tauri-слой (`AppState`)?
2. **Как события доходят до фронта** — глобальные Tauri events, per-call
   `tauri::ipc::Channel`, или команда, висящая до конца стрима?
3. **Что возвращает команда открытия** — результат всего вызова или факт открытия?

Прецедент — ADR-0001: resolve-пайплайн живёт только в ядре, IPC — адаптер.

## Решение

- **Вызов живёт в ядре.** `Sender::open_stream` разделяет с unary-Send ветку
  resolve → builtins → auth → activate и возвращает `StreamCall` — handle в духе
  actor-паттерна (tokio): управление через каналы, тело вызова — отдельная задача,
  порождённая внутри `open_stream`. Реестр `StreamRegistry` (`request_id` →
  `StreamCall`) вместе со Stream store — тоже ядро. `AppState` держит `Arc` на реестр;
  команды `stream_*` — тонкие адаптеры.
- **Дедлайн — в ядре.** Две фазы (Open → connected, Half-close → stream start)
  привязаны к событиям, которые видит только ядро; IPC-гонка для стрима — только cancel.
- **Один `Channel<StreamEventIpc>` на вызов**, tagged union
  `Opened / Headers / Message / End / Fault`. Канал уезжает в задачу ядра через callback
  той же формы, что `Channel::new`.
- **Команда открытия резолвится при `Opened`** («return-at-Opened»): `Ok` = вызов
  открыт, дальше всё в канале; `Err` — только до открытия. Терминал — событие `End`
  (серверный статус) или `Fault` (клиентская терминация после открытия). Cancel идёт
  через реестр (`grpc_cancel` смотрит unary-реестр, затем стримовый) и событием не
  является.

## Рассмотренные альтернативы

- **Реестр стримов в `AppState`, в ядре — только `open_stream`.** Разрезает одну
  сущность по слоям: store (нужны дескрипторы и декод — ядро) и его владелец (IPC).
  Правило времени жизни store — доменное (тикет 08), а не деталь транспорта. Это тот
  же класс «UI/адаптер решил одно, ядро умеет другое», ради которого писался ADR-0001.
- **Глобальные Tauri events.** Документация Tauri: events не для порядка и пропускной
  способности; имя события глобально → фильтрация по `request_id`, гонки `unlisten`.
  Channel даёт порядок и авто-снятие регистрации per-invoke.
- **Pending-until-end** (команда висит до End/Cancel; рекомендация исследования 05).
  Рекомендация исходила из отсутствия реестра задач: без него отмена возможна только
  через drop future команды. С реестром в ядре drop future ничего не рвёт на проводе,
  а возврат команды лишь дублирует канал. Осталась одна дорога для «что случилось»
  (канал) и одна для «удалось ли открыть» (возврат).
- **Две команды `server_streaming_dynamic` / `streaming_dynamic` в транспорте.**
  На проводе одно и то же (`server_streaming` = `once` над `streaming`); вид метода
  решает лишь, чем кормится outbound — забота ядра, не транспорта.

## Последствия

- Инвариант «Send spine в ядре ровно один раз» распространяется на стрим буквально:
  ветка `open_stream` и unary `send` делят resolve → builtins → auth → activate.
- Unary сохраняет IPC-side timeout; у стрима дедлайн в ядре. Асимметрия осознанная;
  унификация unary-как-стрим — вне scope.
- Отмена стрима не через `Notify`/drop future, а через handle — `grpc_cancel`
  становится общей точкой над двумя реестрами.
- Фронт держит только мета и превью; тела, сборка файла и сохранение — команды над
  Stream store. Освобождение store — обязанность фронта (`stream_release`), правило
  одно: пока на `request_id` ссылается хотя бы один шаг.
- Кто предлагает «маленький реестр стримов в `AppState`» или «вернуть результат
  стрима из команды» — сначала сюда.
